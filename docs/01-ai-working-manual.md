## 触发词：原型同步开发

当用户说出“原型同步开发”时，自动进入原型到工程同步 SOP。该触发词表示：用户已经要求把主原型变化同步到开发方案，但尚未授权进入 App 代码开发。

执行顺序：

1. 读取 `docs/prototype/meal-agent-product-prototype.html`，确认主原型最新状态。
2. 对照用户最近讨论和 `docs/TASK_LOG.md`，梳理本轮原型变化。
3. 抽取可工程化内容：页面流转、首页/页面状态机、数据字段、文案、可复用常量、SVG/path/坐标资产、聚合算法、验收边界。
4. 评估真实 App 实现：React Native 可复用部分、不能直接复用的 HTML/浏览器 API、Android/iOS 影响、热更新影响、是否新增原生依赖、是否需要重新打包。
5. 检查并同步 `docs/02-master-blueprint.md`：判断本轮变化是否涉及数据库表字段、TypeScript 类型、常量定义、API 接口或架构约束；凡涉及的，必须先更新蓝图，保持蓝图作为唯一权威来源。常见需更新的蓝图位置：数据库 DDL（新增字段/表）、TS 类型接口、`## 省份数据常量` / `## 算法与大模型分工` 等章节常量、`POST /v1/meal/analyze` 等接口规范、Sprint 任务描述（简化版）。
   **蓝图过滤原则（防止原型实现细节污染蓝图）**：只写"是什么 + 业务规则 + 数据定义 + 平台无关的 UX 交互模式"，不写"怎么实现"。具体边界：
   - ✅ 可写：字段名/类型/枚举值、常量数组/映射、业务约束（如 append-only）、UX 模式描述（如"底部面板选择器"、"分组 chip"）
   - ❌ 不写：浏览器专用 API（`window.prompt`、`innerHTML`、`onclick`）、HTML DOM 结构、CSS 类名/内联样式、原型内部回调机制（如 `window.__selectorPick`）
6. 同步当前阶段开发文档，在任务表前新增”主原型同步修订（日期 + 功能名）”节，并同步修正对应任务行，避免后续只看任务表时读到旧口径。
   **”主原型同步修订”节的写法必须使用两栏结构**，每个功能点分开写：
   ```
   **【业务规格】**   ← 工程实现的唯一依据，平台无关
   - 字段、枚举值、业务约束、UX 交互意图

   **【原型参考】**   ← 仅供理解交互意图，不是实现要求
   - 原型使用的函数名/机制（标注”原型专用”）
   - React Native 对应实现方向（标注”App 对应”）
   ```
   `【业务规格】` 遵守步骤 5 的蓝图过滤原则（不写浏览器 API、DOM、CSS）；`【原型参考】` 可写原型内部实现，但必须注明”原型专用，不得照搬”。工程师只需阅读 `【业务规格】`，`【原型参考】` 仅供理解背景。
7. 同步当前阶段验收文档，让验收口径与主原型和任务表一致。
8. **检查 App 代码是否已有对应实现**：对照本轮变更涉及的任务（如 T2-05），检查 `src/` / `app/` 中是否已有实现代码。若已实现，必须在 `docs/CURRENT_WORK.md` 中明确标注”⚠️ 代码待回写：[文件路径] 与新口径不一致，需另起任务对齐”；若未实现，无需额外标注。**严禁在本步骤直接修改 App 代码**，代码回写必须等用户确认文档定稿后另起 L2 任务。
9. 更新 `docs/CURRENT_WORK.md` 和 `docs/TASK_LOG.md`，记录仍处于方案同步阶段，未进入 App 开发。
10. 向用户总结同步范围、不可复用风险、已发现的代码待回写项、下一步需要确认的点。

完成标准：

- **蓝图、阶段开发文档、任务表、阶段验收文档**四层不再互相冲突。
- 蓝图中凡有变化的字段/常量/接口，必须在本轮同步完成，不能留到后续专项任务补。
- 所有旧口径必须被删除、改写或明确标注为历史兼容，不允许只靠口头解释覆盖。
- 真实工程可复用的资产和规则必须有明确落点；不能复用的部分必须写明替代方案。
- 用户明确确认原型和同步开发方案定稿前，不得修改 App 业务代码。

## 触发词：进入开发

当用户说出"进入开发"时，自动进入开发就绪门控检查。该触发词表示：需求阶段已完成（原型和方案均已用户确认），准备开始 L2 开发，但必须先通过两个门控。

**两个门控必须顺序执行**：门控1通过后才能执行门控2，因为补全方案可能引入新的数据或接口依赖，影响门控2的检查范围。

### 门控1：原型 ↔ 方案完整性检查

目标：确认原型中的每个页面、状态、交互，在当前阶段开发文档中都有对应描述，没有遗漏。

执行步骤：

1. 读取主原型 `docs/prototype/meal-agent-product-prototype.html`，逐页列出所有页面和关键状态。
2. 读取当前阶段开发文档 `docs/phases/phase-*.md`，逐项比对。
3. 输出覆盖清单（三列）：**原型内容 / 方案对应描述 / 状态**
   - ✅ 已覆盖
   - ⚠️ 描述不完整
   - ❌ 未覆盖
4. 有 ⚠️ 或 ❌ 项时，先补完方案（L1 文档任务），用户确认后再执行门控2。
5. 所有项均为 ✅ 时，门控1通过。

### 门控2：Pre-Flight 技术可行性检查

目标：确认方案中依赖的数据字段、接口能力、原生依赖在当前基础设施中均已就绪或已明确排期。

执行步骤：

1. **数据合约**：列出原型和方案中涉及的所有数据字段 → 逐一对照 `src/types/meal.ts`，列出缺口。
2. **接口合约**：列出原型中依赖的 AI / 后端能力 → 对照 FastAPI 现有路由，列出缺口。
3. **原生能力**：是否需要新增原生依赖或重新打包？
4. 输出就绪清单：
   - ✅ 已就绪
   - ⚠️ 有缺口，已排入 L2 第一批任务
   - ❌ 有缺口，未排期（阻塞开发，必须先排期）
5. 所有 ❌ 排期后降为 ⚠️，门控2通过。

### 完成标准

- 门控1和门控2均无 ❌ 项。
- 用户明确确认两份清单。
- 所有 ⚠️ 缺口已写入即将开始的 L2 第一批任务说明。
- 完成后方可写 `TASK_LOG` START，正式进入 L2 开发。

## 任务分级

为避免流程过重，任务按风险分级执行：

- L0 只读评审 / 问答：只读相关文档和代码；不改文件时不新增 `TASK_LOG`，最终回复说明原因。
- L1 文档治理 / 原型小改：读取 `00-INDEX`、`CURRENT_WORK`、`TASK_LOG`、`LESSONS_INDEX` 和目标文件；不涉及真实资源时可不读完整资源索引；必须写 START / END。
- L2 App 业务代码 / 数据层：读取蓝图、阶段文档、验收文档和相关代码；按影响范围运行 lint/typecheck/test。
- L3 原生依赖 / 数据库 / AI provider / 真实联调 / 部署：必须读取资源索引、确认用户授权、记录真实资源验收口径；不得回显真实密钥。

并行流程治理任务不得覆盖当前产品任务指针。`docs/CURRENT_WORK.md` 应保留当前产品任务，治理任务写入“当前并行治理任务”或交接摘要。

## 开始和结束记录

任何 Agent 接手开发都必须留下可追溯记录。

`docs/TASK_LOG.md` 的任务标题必须带唯一递增编号，格式为：

```text
##001 2026-05-16 00:44:11 +08:00 - Codex - START
##001 2026-05-16 00:50:03 +08:00 - Codex - END
```

编号生成规则：每次新增任务记录前，扫描现有 `##001` 这类标题编号，取最大编号 + 1；如果没有编号，从 `001` 开始。同一个任务的 START / END 使用同一个编号。`001` 到 `999` 固定三位补零，超过 `999` 后自然递增为 `1000`、`1001`。

### 开始前

在 `docs/TASK_LOG.md` 新增开始记录，至少包含：

- 唯一任务编号和开始时间（含时区）。
- Agent 名称，例如 Codex、Claude、人工。
- 阶段 / Sprint / 任务编号。
- 本次目标。
- 预计触碰范围。
- 是否需要用户批准的事项。

同步更新 `docs/CURRENT_WORK.md`：

- 当前阶段。
- 当前 Sprint。
- 当前任务编号。
- 当前状态。
- 阻塞项。
- 下一步。

### 结束前

先打开当前阶段对应的 `docs/acceptance/phase-*.md`，逐条执行验收。每一项必须标记为：

- `PASS`：已完成并已验证。
- `PARTIAL`：部分完成，必须写明缺口。
- `FAIL`：未完成或验证失败，必须写明原因。
- `N/A`：本次任务不适用，必须写明原因。

在 `docs/TASK_LOG.md` 补结束记录，至少包含：

- 与 START 相同的唯一任务编号和结束时间（含时区）。
- 完成内容。
- 修改文件。
- 验收文档。
- 逐条验收结果。
- 本任务验收。
- 阶段验收影响范围。
- 验证命令和结果。
- 未能验证的项目。
- 需要人工/真机/外部服务验证的项目。
- Android/iOS 影响。
- 热更新影响。
- 是否需要重新打包。
- 本次问题-解决方案-经验教训。
- 经验索引编号，如本次新增或复用了 `docs/lessons/LESSONS_INDEX.md` 条目。
- 遗留问题和下一步建议。

如果没有逐条验收记录，当前任务不得标记为完成。

小任务的验收必须写清“本任务通过了什么”，以及“只影响哪些阶段验收项”。不得把原型小改、文档治理或局部修复写成整个阶段 `PASS`。

同步更新 `docs/CURRENT_WORK.md`，让下一个 Agent 能直接接手。

## 经验教训索引

`docs/TASK_LOG.md` 负责记录本次现场，`docs/lessons/LESSONS_INDEX.md` 负责沉淀可复用经验。两者必须互相引用。

后续 AI 遇到问题时必须先用关键词搜索经验索引，再对照条目的“适用范围”和“触发症状”。确认是同类问题后，才能复用“已验证解决方案”；如果症状不一致，只能作为排查参考，不得机械套用。

只有满足以下至少一项的问题才进入经验索引：

- 涉及真实联调、密钥、Supabase、EAS、真机、AI provider、数据库、构建或部署。
- 容易被多个 AI 重复踩坑。
- 已经有明确根因和已验证解决方案。
- 能沉淀为通用 SOP 或下一个项目可复用规则。
- 影响排查效率明显，预计复用后能节省大量时间。

不得进入经验索引的内容：

- 一次性拼写、格式、临时网络抖动。
- 没有验证过的猜测。
- 只适用于当前文件局部的小问题。
- 会泄露真实密钥、用户隐私或完整 raw response 的细节。

## 开发前确认

执行代码修改前必须完成：

- 读取现有代码实现方式。
- 更新 `docs/TASK_LOG.md` 开始记录。
- 更新 `docs/CURRENT_WORK.md` 当前任务指针。
- 判断任务属于哪个 MVP / Sprint / 任务编号。
- 明确是否需要原生依赖、数据库 migration、AI secret、FastAPI、Supabase 或部署配置。
- 若涉及真实联调、数据库 migration、AI provider、云资源、真机验收或数据导入，必须先读取 `docs/resources/RESOURCE_REGISTRY.md`，确认资源状态、真实值存放位置、验证方式和缺失降级策略。
- 若涉及新增原生依赖、迁移 monorepo、接真实 AI secret、创建 FastAPI 服务、创建 Supabase migrations，必须先得到用户明确批准。

## 资源与密钥规则

- 资源索引只记录资源名称、用途、变量名、存放位置、状态和验证方式。
- 禁止把真实密码、token、API key、service role key、数据库密码写入仓库文档、代码、日志或最终回复。
- 移动端 Expo 环境只能使用 `EXPO_PUBLIC_*` 公开变量；后端私密变量必须放在 `services/ai/.env`、本机环境、EAS secrets 或用户密码管理器。
- 真实值是否已配置，只能记录为“已配置/未配置/已验证/未验证”，不得回显真实值。
- 缺少真实资源时，验收结果必须标记 `PARTIAL` / `FAIL` / `N/A`，不得写 `PASS`。
- 任何真实资源状态发生变化后，必须同步更新 `docs/resources/RESOURCE_REGISTRY.md`；状态只能写 `PASS` / `PARTIAL` / `待验证` 等口径和验证条件，不得写真实值。

## 阶段文档使用规则

- 阶段开发文档只定义目标、范围、任务和交付物。
- 阶段验收文档只定义完成标准、检查命令、数据验收和风险。
- 阶段开发文档必须包含“本阶段必须引用的蓝图章节”，覆盖该阶段相关的 Schema、API、算法、Prompt、RLS、安全、UserContext、环境变量和 CI/CD 约束。
- Agent 执行阶段任务时，必须先读取该引用清单中的总蓝图片段，不得只看阶段任务表就开始开发。
- 当阶段文档与总蓝图冲突时，以 `docs/02-master-blueprint.md` 为准，并先修正文档，不直接写代码。
- `_archive/` 只能作为历史参考。

